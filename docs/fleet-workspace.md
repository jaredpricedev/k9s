# Explicit two-context workload facts

This optional TK21 groundwork addresses part of [#65](https://github.com/jaredpricedev/k9s/issues/65). Concrete human demand, operator studies and product acceptance remain unmeasured. The proposed task is to inspect a named native workload in two explicitly chosen contexts. This increment does not complete the broader fleet workspace, certificate or named-source drift backlog and does not establish application equivalence.

From a selected native Deployment, StatefulSet, DaemonSet or Job, run `:fleet peer-context`. The primary context, GVR, namespace, name and UID are captured from the selection. Alternatively run `:fleet peer-context deployments namespace name` (also `statefulsets`, `daemonsets`, `jobs`) to request an explicit name. Its first successful primary observation captures the primary UID. A changed primary UID requires reopening. Each peer GET captures its own independent UID. Matching names or labels do not prove a logical application or a cross-cluster identity.

No context discovery, global context switch, resource list, Pod scan, Secret read or external provider is used. Each context gets an independent configuration snapshot and a read-only dynamic actor. Collection is on demand, with two concurrent context workers, a three-second per-read timeout, eight-second per-context budget and twelve-second collection budget. Configuration setup runs behind the parent cancellation boundary; configuration loader work already started may finish after cancellation. Only the exact namespaced workload and an optional exact Namespace UID are requested. No raw objects, annotations, environment or credential values are retained. One snapshot per open view retains at most 64 declared-image and reported-status facts per context (each retained value bounded to 512 runes); each failed refresh preserves that context's prior facts and labels them retained.

The view shows effective sanitized API authority, context, namespace, object UID, resourceVersion and capture time. Equal API authority and Namespace UID produce a warning that the contexts may alias one cluster. They are not assumed to represent two independent clusters. API authority alone is not a cluster identity proof. A named absence requires a Kubernetes APIStatus with code 404, reason NotFound and matching group/resource/name; proxy or unexpected responses remain unavailable. Denied, canceled, timeout, unavailable and missing status are explicit.

Images are **template declarations**. They are not resolved runtime digests or proof of runtime adoption. Generation, replica counts and conditions are reported facts; no compatibility or rollout-health inference is made. Missing status stays unknown. Chart version, application release and Git revision are outside this source's coverage.

At 100 columns or more the two sources are independent columns; at 80×24, 60 columns and 40×12 they stack in a scrollable native detail view. `r` refreshes, `/` searches, normal detail keys scroll and `Esc` returns. Query and scroll survive refresh. Destination changes prevent further reads, and leaving cancels work; disconnected browser polling retains the workspace. Below the supported task minimum the standard size notice is shown. Labels carry meaning in monochrome/no-icons mode. The layout has no nested border and uses three scope/source/coverage header lines plus one action line.

Fixture tests cover actor count, exact GET scope, independent peer failure, independent UIDs, primary replacement, strict 404, alias warning, unsupported kinds, cancellation, credential exclusion, native narrow frames, input and disconnected poller retention. These checks are not live Kubernetes validation or an operator demand study. Proposed acceptance work remains: collect concrete operator scenarios, evaluate interpretation and destination awareness, and decide whether broader app/certificate/drift sources justify explicit additional budgets.

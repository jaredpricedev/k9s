# Native security declaration review

`:security-review` opens from a selected namespaced Pod, Deployment, StatefulSet, DaemonSet, Job, or CronJob. It captures the selected context, namespace, name, UID, and destination revision, then performs one exact namespaced GET. The view discards a response when the destination changes or the returned UID/name/namespace/API-version/kind does not match the captured native identity. It performs no namespace-wide list, arbitrary-context lookup, scanner invocation, or write.

The Facts tab presents host namespace flags present in the captured API object, ServiceAccount and token automount fields, hostPath volumes and container volume mounts, security-context declarations for init, application, and ephemeral containers, declared images, and available status image IDs. The Gaps tab identifies what the native read does not establish. The Evidence tab records the exact source identity, resource version, capture time, and provider availability. Search and scrolling use the shared Details view; `1`–`3` and Tab select sections, `r` refreshes, and Escape returns through the normal view stack. The review is retained across a disconnected browsing session, and the shared action catalog exposes it for supported selections. When a ServiceAccount is declared, the existing `:can s:<name>` RBAC subject-rules view is suggested, with an active-namespace reminder; its rules do not establish runtime token use or effective authorization.

API fields may include Kubernetes defaults or admission changes; this read does not establish original authorship. Omitted fields remain unknown. This view makes no safety score, pass/fail verdict, admission, enforcement, effective-runtime, or traffic claim. Scanner and admission-policy adapters, rule versions, coverage, and exceptions remain unsupported and unconfigured. Legacy AppArmor annotation values are excluded along with all other annotation values. The projection retains only an allowlist of typed facts; it does not read Secrets or retain environment values, arbitrary object fields, or raw API bodies.

This native screen is groundwork for bounded declaration evidence. Human demand validation and a configured scanner or admission-policy provider are still required before making provider-backed security or policy claims. The scenario and provider-selection decision in [issue #67](https://github.com/jaredpricedev/k9s/issues/67) remains open.

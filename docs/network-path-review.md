# Network path review

Select a native Service with a captured UID, then use `:network-review` or its Actions entry. The default scope reads current configuration in the Service namespace. `:network-review route-ns=apps,edge` adds at most eight explicit route namespaces; it widens Ingress/HTTPRoute reads, while Pod, EndpointSlice and NetworkPolicy reads remain in the Service namespace. Gateway parents are read only by declared exact namespace/name references. Namespace selectors use exact named Namespace GETs; there is no all-namespace discovery.

The review joins Service ports and selector, relative Service DNS name, authored Pod DNS policy/configuration, EndpointSlice addresses/ports/conditions and UID-verified current Pods. It includes matching Ingress backends and native Gateway API v1 HTTPRoute references, listener section/port/hostname configuration, allowedRoutes namespace/kind limits, reported parent/controller conditions and v1beta1 ReferenceGrants. An unavailable API/version, permission, parent/backend kind, namespace selector or observed generation remains a gap. It never substitutes a recreated Service or endpoint Pod for a captured UID.

Configured paths, current endpoint readiness, controller reports and selecting NetworkPolicy candidates remain separate from proven connectivity and policy authorization. Runtime resolver files, cluster DNS suffix, certificate keys, HTTP headers and Secret content are not collected. A tag/hostname/IP or reported Pod name cannot establish a Service identity or current Pod UID. A quiet section does not prove health or absence of traffic.

Tabs 1–7 are Path, DNS, Backends, Routes, Policies, Flows and Evidence; Tab cycles them. `j`/`k` selects retained source rows, Enter opens supporting inspection for the captured UID, and `v` shows exact retained projection/scope/time/coverage. Local search and tab selection survive evidence navigation, denied refresh and resize. `r` explicitly refreshes configuration. Failed/changed destinations retain prior evidence and require reopening.

`h` explicitly opens the existing native Hubble peer/conversation view for the obtained backend names. Relay configuration is the captured context's configuration. It does not enable L7, launch an endpoint probe or create a forwarding session. Native Hubble owns filter/freeze/reconnect and peer/conversation state. Returning stops the stream and composes its retained window into Flows: reported peer pairs, drop groups, policy attribution when reported, and bounded reported DNS query/answer/CNAME/type/latency fields. Zero/unreported latency stays unknown; an empty answer or query record is not a failed lookup. In Flows, `p`/`t` toggle reported source/destination pins and `P` toggles a directed reported conversation. Up to 32 in-memory pins retain context and creation time independently of current rows; a vanished report is neither a clearance nor a proven dependency. Unknown peers cannot become conversation pins. API source times, local observation window, buffer eviction, omitted flow projections/drop groups, reported loss and node/Relay coverage remain explicit. Reopening the native observation retains its stopped state; reconnect is explicit and can leave a gap.

Configuration collection has a 15-second deadline, 2-second query deadlines, two pages of 64 candidates per namespaced query, at most 16 exact Gateway reads and 16 extra endpoint-UID Pod reads, 128 obtained Pods and 512 projected records. Limits/invalid references/denied/absent/canceled reads remain visible. Snapshots are retained in memory; source navigation is read-only and UID checked by native inspection. Optional historical/fleet identity mapping and active probes are outside this native configuration/observation workflow.

Verification uses typed projections, dynamic-client fakes and native terminal-cell fixtures at 120×34, 80×24, 60×24 and the 40×12 available task region, including no-icons/monochrome and below-minimum state retention. These checks are not a live-cluster, real PTY or operator study.
